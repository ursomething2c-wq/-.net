# Концепция: Оттоку.net — сервис по продлению для отдела продаж

*Мастер-документ — собирает всю концепцию в одном месте: архитектуру, роли, компоненты, зафиксированные решения и статус реализации. Рабочий прототип части функциональности уже собран (см. раздел 15).*

## 1. Что это и зачем

Внутреннее приложение для тренировки отдела продаж на тему **продления подписки Битрикс24**. Сотрудник ведёт текстовый диалог с ИИ-клиентом, собранным из реальных кейсов, и получает разбор ошибок сразу после диалога. База кейсов пополняется из настоящих звонков и одновременно служит двум целям: обучает бота-клиента и обучает живых сотрудников напрямую — из одного источника (звонка) получаются оба представления.

## 2. Роли и авторизация

Три роли, каждый пользователь заходит под одной из них:

| Роль | Возможности |
|---|---|
| **Сотрудник** | Чат-тренировка, Прослушивание, Личный кабинет (свой прогресс) |
| **Админ** | Всё то же + Кейсы (проверка/правка), Разбор звонков, вид «Прогресс команды» в Личном кабинете |
| **Суперадмин** (главный админ, ты) | Всё то же + единоличное право редактировать промпты во вкладке «Промпты» (системный промпт и промпт оценки) и назначать/снимать права администратора другим сотрудникам |

**Авторизация — по корпоративной почте.** Пользователь вводит email, приложение сверяет его с директорией сотрудников (email → имя → роль) и пускает под соответствующей ролью. Роль не переключается вручную после входа — она жёстко привязана к аккаунту, как и должно быть в реальном логине.

*Ограничение прототипа:* полноценная email-аутентификация (код на почту, magic link, пароль) требует реального сервера, отправляющего письма, — в прототипе её нет физически. Сейчас есть работающая имитация: сверка введённого email со списком сотрудников на стороне приложения, плюс отдельный «демо-вход» — тот же слайдер по ролям, что раньше был в шапке приложения, для быстрого переключения между ролями при показе. Для боевого приложения понадобится настоящий бэкенд для аутентификации (см. раздел 15).

## 3. Компоненты приложения (обзор)

| Компонент | Назначение | Кто видит |
|---|---|---|
| Главная | Дашборд по роли — статистика и переходы | Все |
| Разбор звонков | Загрузка реального звонка → обезличивание → два выхода | Админ, суперадмин |
| Прослушивание | Библиотека учебных кейсов из реальных звонков | Все |
| Админ-панель кейсов | Проверка, правка, статус кейсов | Админ, суперадмин |
| Промпты | Редактирование системного промпта и промпта оценки | Только суперадмин |
| Чат Оттоку.net | Диалог сотрудника с ИИ-клиентом | Все |
| Модуль оценки | Разбор ошибок после диалога | Все |
| Личный кабинет | Мой прогресс / Прогресс команды | Все (вид зависит от роли) |

*Две базы кейсов («Компания» и «Личность») — не отдельный экран, а хранилище данных, с которым работают «Разбор звонков» и «Админ-панель кейсов» (раздел 5).*

## 4. Главная страница (по ролям)

Один и тот же экран показывает разное в зависимости от роли — стартовая вкладка после входа.

**Вид админа/суперадмина:** заголовок «Панель администратора», четыре плашки со статистикой (кейсов всего, кейсов из реальных звонков, звонков в обработке — то есть разобранных, но ещё не превращённых в кейс бота, сотрудников тренируется — считается динамически по реальной активности), и карточки-переходы: «Разбор звонков», «Кейсы», «Прослушивание», и только у суперадмина — «Промпты».

**Вид сотрудника:** персональное приветствие по имени, карточки-переходы: «Чат-тренировка», «Прослушивание», «Личный кабинет».

## 5. Хранилище кейсов: две базы

### 5.1. База кейсов «Компания»

Факты о компании-клиенте на продлении.

| Поле | Описание |
|---|---|
| `id` | Уникальный ID |
| `title` | Кодовое название компании |
| `industry` | Отрасль |
| `staff` | Размер компании |
| `tools_used` | Что из Битрикс24 сейчас используется |
| `renewal_context` | Почему разговор происходит сейчас (истекает тариф, риск оттока, апсейл и т.п.) |
| `status` | pending / approved / archived |
| `sourceCallId` | Если кейс получен из реального звонка — ссылка на него (см. раздел 6) |

### 5.2. База кейсов «Личность»

Характер и манера общения клиента — независима от компании. Ярких, различимых типов личности объективно немного, поэтому эта база — небольшой курируемый список, а не по одной записи на каждый разобранный звонок (см. проверку на совпадение в разделе 6).

| Поле | Описание |
|---|---|
| `id` | Уникальный ID |
| `name` | Название типа личности |
| `personality_description` | Черты характера, манера речи |
| `typical_objections` | Типичные возражения этого типа |
| `status` | pending / approved / archived |
| `sourceCallId` | Ссылка(и) на звонок(и)-источник, если есть — один и тот же типаж личности может быть связан сразу с несколькими звонками |

**Любая компания комбинируется с любой личностью** — независимые сущности, в этом смысл рандомизации (раздел 8).

## 6. Разбор звонков: один источник — два выхода

Ключевая идея: из одной загрузки реального звонка (например, через BitrixGPT) получаются сразу **два разных представления для двух разных задач**, плюс процесс подразумевает регулярное, повторяемое пополнение базы — это не разовый скрипт, а действие, которое админ может выполнять по каждому новому звонку.

**Шаг 1 — Загрузка.** Админ вставляет расшифровку или пересказ реального звонка.

**Шаг 2 — Обезличивание** (отдельный проход):
- Имена людей (сотрудника и клиента) заменяются на другие правдоподобные
- Название компании — на нейтральное вымышленное кодовое название
- Телефоны, email, адреса — удаляются или заменяются на вымышленные плейсхолдеры
- Структура и реплики диалога сохраняются — переписывается тот же разговор с заменёнными данными, а не пересказ
- Если из текста не ясны сфера деятельности или число сотрудников — они правдоподобно додумываются, и это явно помечается («Придумано: сфера, количество сотрудников»), чтобы админ видел, где реальные данные, а где домысел

**Шаг 3 — Верификация обезличивания** (обязательна, двойная — до этого шага текст никуда не публикуется):
- **Автоматическая проверка (второй, отдельный LLM-проход).** Специальный промпт получает только обезличенный текст и ищет остаточные идентифицирующие данные — не пропущенные имена, названия, телефоны, email, адреса, узнаваемые формулировки. Возвращает список находок (если есть) с указанием, что именно и где похоже на утечку.
- **Обязательная проверка админом.** Админ видит исходный обезличенный текст и результат автоматической проверки рядом, правит вручную при необходимости и явно подтверждает («Подтверждаю обезличивание») — без этого подтверждения кейс не может перейти к шагу 4 и не может быть сохранён ни в «Кейсы», ни в «Прослушивание» (последнее видят все сотрудники, поэтому гейт обязателен).
- **Напоминание о проверке.** Если в очереди на верификацию или на одобрение кейсов (раздел 7) есть необработанные звонки, админ и суперадмин получают уведомление в Личном кабинете каждый вторник — до тех пор, пока очередь не разобрана.

**Шаг 4 — Разбор, один проход, два выхода:**
- **Выход 1 — карточка для бота.** Компактные структурированные данные: company_case + personality_case — те же поля, что в разделе 5.
  - **company_case** — всегда новая запись, уходит на проверку в базу кейсов со статусом `pending`.
  - **personality_case** — автоматическое сравнение с уже одобренными личностями по трём измерениям (манера речи, доминирующие возражения, эмоциональный тон), с выводом ближайшего совпадения и оценкой схожести. Админ видит это сравнение при проверке и решает: типаж совпадает — звонок добавляется как ещё один `sourceCallId` к существующей личности; типаж новый — предлагается новая personality_case на проверку со статусом `pending`. Итоговое решение остаётся за админом, но опирается на структурированное сравнение, а не на свободную догадку — это снижает разброс решений между разными админами.
- **Выход 2 — учебный кейс для сотрудников.** Связный разбор для чтения живыми людьми: короткое название, описание ситуации простым языком, ключевые моменты диалога (что сделал сотрудник в конкретный момент), вердикт (чем закончилось) и практические уроки. Это не то же самое, что карточка для бота, — она читаема человеком, а не служит структурированными данными для промпта.

**Шаг 5 — Сохранение.** Админ решает: сохранить оба выхода (карточка бота — на проверку в «Кейсы», учебный материал — в «Прослушивание»), или только учебный материал, если карточка для бота получилась неудачной.

**Обработка большого объёма (пакетная загрузка).** Источник пополнения — база из ~1200 реальных звонков. Обрабатывать их по одному вручную нецелесообразно при обязательной двойной верификации на каждом: это будет узким местом на входе. Нужен пакетный режим — загрузка нескольких звонков за раз, каждый проходит шаги 2–4 независимо и параллельно, а результаты попадают в общую очередь на проверку (раздел 7, фильтр «только на проверке»), которую админ разбирает сессиями, а не по одному звонку. Без этого объём в 1200 звонков не конвертируется в кейсы за разумное время.

## 7. Админ-панель кейсов

Ничего не попадает в рандомизацию без ручного одобрения — это ключевое требование первого этапа.

- Список кейсов (отдельно «Компания», отдельно «Личность») со статусами `на проверке` / `одобрен` / `архив`
- Просмотр и **редактирование прямо в интерфейсе**
- Изменение статуса: одобрить → доступен для рандомизации; в архив → исключается
- Фильтр «только на проверке» — быстро пройти очередь новых кейсов, в том числе сгенерированных из звонков

## 8. Логика рандомизации

Перед стартом чата (или по запросу «новый сценарий»):
1. Случайный **одобренный** кейс из базы «Компания»
2. Случайный **одобренный** кейс из базы «Личность»
3. Сборка единого промпта клиента из фактов о компании + манеры поведения личности
4. Передача в системный промпт бота-клиента

**Анти-повтор:** сочетание компания+личность не должно повторяться подряд у одного и того же сотрудника. Приложение хранит последнюю использованную пару на пользователя и исключает её при следующей генерации; если одобренных кейсов слишком мало и все пары уже использовались — ограничение снимается только для самой последней пары, чтобы не блокировать генерацию совсем.

## 9. Архитектура промптов (4 слота)

По аналогии с существующим ботом «Менеджер по продажам» — раздельное хранение, чтобы оценщик не видел промпты личности/компании и не подглядывал в оценке:

| Слот | Содержание | Кто видит | Как формируется |
|---|---|---|---|
| Промпт компании | Факты о компании-клиенте | Только бот-клиент | Собирается автоматически из полей одобренного кейса «Компания» по заданной структуре (раздел 5.1) — редактируется косвенно, через правку кейса в админ-панели кейсов (раздел 7) |
| Промпт личности | Характер, манера речи, возражения | Только бот-клиент | Пишется и правится вручную в базе «Личность» (раздел 7) — не собирается по шаблону, потому что ярких типов личности объективно немного (раздел 5.2, 6) |
| Системный промпт | Инструкции боту: как себя вести, как завершать диалог | Только бот-клиент | Редактируется только суперадмином, во вкладке «Промпты» |
| Промпт оценки | Критерии оценки, формат ответа | Только модуль оценки, отдельный вызов — без промптов личности/компании, только текст диалога | Редактируется только суперадмином, во вкладке «Промпты» |

Все четыре редактируются независимо, без деплоя кода.

**Вкладка «Промпты» — только суперадмин.** Отдельный экран (раздел 3), недоступный обычным администраторам, объединяет редактирование системного промпта и промпта оценки. Правка прямо в интерфейсе, с сохранением истории изменений (кто и когда правил) — на случай отката.

## 10. Чат Оттоку.net

- Текстовый диалог сотрудника с ИИ-клиентом
- ИИ-клиент отвечает согласно собранному промпту (компания + личность + системный)
- Диалог завершается естественно (клиент дошёл до решения — согласие, отказ или следующий шаг) либо по лимиту реплик — 40 реплик суммарно (20 от сотрудника + 20 от бота)

## 11. Модуль оценки

После диалога:
1. Только текст реплик (без промптов клиента) передаётся в промпт оценки
2. Оценщик возвращает баллы по критериям + текстовый комментарий с конкретными ошибками, с обязательной привязкой каждой оценки к конкретной реплике или моменту диалога (а не только абстрактный балл) — это делает вердикт проверяемым при оспаривании
3. Результат показывается сотруднику сразу

**Оспаривание оценки.** Кнопка «Оспорить оценку» на экране результата, с опциональным комментарием сотрудника («не согласен, потому что…»). Заявка уходит в очередь на разбор админу/суперадмину (аналогично очереди кейсов, раздел 7): админ видит транскрипт, вердикт оценщика с привязкой к репликам и комментарий сотрудника, может вручную скорректировать баллы. Итоговая карточка хранит оба значения — исходную оценку ИИ и итоговую (после пересмотра, если он был), с указанием, кто и когда пересмотрел. Сотрудник получает уведомление о результате пересмотра.

### Критерии оценки для продления

Адаптированы из пяти критериев тест-ботов внедрения под контекст удержания клиента:

| № | Критерий | Что оценивается |
|---|---|---|
| 1 | Установление контакта и диагностика статуса | Приветствие, уточнение текущего использования и повода для разговора |
| 2 | Выявление причины сомнений | Докопался ли до реальной причины колебаний, а не принял первую формулировку |
| 3 | Аргументация ценности использования | Показана ли ценность используемого функционала и релевантных возможностей |
| 4 | Работа с возражениями по продлению | Обработка возражений: цена, «подумаем», конкуренты, недоиспользование |
| 5 | Закрытие на продление | Доведён ли диалог до конкретного результата |

*Точные веса баллов по каждому критерию — предмет отдельной проработки с методологом.*

## 12. Прослушивание

Библиотека учебных кейсов (выход 2 из раздела 6), доступна всем ролям. Список карточек, каждая раскрывается в: ситуацию простым языком, ключевые моменты диалога, вердикт, практические уроки. Обезличенный текст оригинального звонка доступен по клику отдельно, для тех, кто хочет свериться с первоисточником. Кейсы, ставшие карточкой для бота, помечены бейджем «стал кейсом бота».

## 13. Личный кабинет

Два подраздела: «Мой прогресс» (все роли) и «Прогресс команды» (только админ/суперадмин, то есть руководитель) — видимость зависит от роли.

**Мой прогресс (все роли):**
- Полная история всех попыток (не разовое использование Оттоку.net) — каждая с датой, итоговым баллом, разбором ошибок и транскриптом по клику
- Блок «Комментарий руководителя», если руководитель оставил и сделал видимым

**Прогресс команды (админ/суперадмин):**
- Детальный разбор по каждому сотруднику — вся история, баллы, комментарии оценки
- Свой комментарий сотруднику — **свободная форма, без периодичности и дедлайнов**
- Переключатель видимости комментария («показать сотруднику» / «скрыто») — по умолчанию скрыто
- История всех оставленных ранее комментариев

Сотрудник результатов коллег не видит — только свой собственный прогресс. Это осознанное ограничение: публичная видимость баллов коллег создавала риск, что сотрудники станут реже тренироваться или избегать сложных кейсов из страха перед чужой оценкой, что прямо противоречит цели инструмента (частая, безопасная тренировка на ошибках).

## 14. Хранение данных и технологии

БД внутри самого приложения (SQLite или PostgreSQL — в зависимости от развёртывания). Для этого объёма данных (сотни-тысячи кейсов, десятки сотрудников, история попыток) это лёгкая нагрузка: SQLite спокойно работает с базами на десятки гигабайт, а для параллельной записи (несколько сотрудников проходят диалоги одновременно) подойдёт PostgreSQL, рассчитанный именно на конкурентную запись. Риск «тяжеловесности» возникает на масштабах в тысячи одновременных пользователей — здесь это не тот случай.

## 15. Статус: прототип vs продакшен

Рабочий прототип части этой концепции уже собран и продемонстрирован (артефакт `renewal_trainer_prototype.jsx`) — с реальной логикой рандомизации, чатом с ИИ-клиентом через API, оценкой по 5 критериям, разбором звонков в два выхода, обезличиванием, библиотекой «Прослушивание», личным кабинетом и страницей входа.

**Честно об ограничениях прототипа** — то, что в боевом приложении должно быть устроено иначе:

| В прототипе | В продакшене нужно |
|---|---|
| Встроенное key-value хранилище артефакта | Настоящая БД (SQLite/PostgreSQL) |
| Email сверяется со списком в коде браузера | Настоящий бэкенд-логин: код на почту или magic link, сервер проверяет, а не браузер |
| «Демо-вход» с ручным выбором роли | Убрать полностью — роль всегда только из аккаунта |
| API-ключ вызывается прямо из браузера | Вызовы к модели — только через сервер, ключ никогда не должен быть в браузере |
| Нет постоянного хостинга — живёт в чате | Отдельный домен, доступный команде каждый день |

## 16. Этапы реализации

| Этап | Содержание |
|---|---|
| 1 | Первый релиз: БД внутри приложения + бэкенд-авторизация по почте + админ-панель + разбор звонков (обезличивание + двойная верификация + два выхода + пакетная загрузка) + сборщик рандомизации с анти-повтором + 4 слота промптов + текстовый чат + модуль оценки по 5 критериям с оспариванием + Прослушивание + Личный кабинет + Главная по ролям |
| 2 | Уточнение весов критериев и порога зачёта с методологом, донастройка по итогам первых прогонов |
| 3 | Аналитика по прогонам: сколько диалогов, средние баллы, частые ошибки — если нужно |

## 17. Зафиксированные решения

1. Хранение — БД внутри приложения, не Google Sheets/локальный файл
2. Рандомизация — с анти-повтором на пользователя
3. Формат чата — текстовый
4. Критерии оценки — пять новых критериев под контекст продления
5. Доступ к админ-панели — многоуровневый, суперадмин назначает права
6. История — многопользовательская, хранится вся история попыток
7. Комментарий руководителя — свободный, без периодичности
8. Разбор звонков даёт два раздельных выхода из одного источника: карточка для бота + учебный кейс для сотрудников
9. Обезличивание — отдельный шаг перед разбором, с честной пометкой придуманных данных
10. Авторизация — по email, роль жёстко привязана к аккаунту, не переключается вручную после входа
11. Системный промпт и промпт оценки редактируются только суперадмином, во вкладке «Промпты»
12. Промпт компании собирается автоматически из полей кейса; промпт личности пишется и правится вручную — типов личности объективно немного
13. При разборе звонка новая личность создаётся только если похожего типажа ещё нет в базе (по структурированному автоматическому сравнению); иначе звонок привязывается к существующей личности
14. Лимит реплик в чате Оттоку.net — 40 суммарно (20 от сотрудника + 20 от бота)
15. Обезличивание проходит обязательную двойную верификацию (второй LLM-проход + подтверждение админа) до сохранения в «Кейсы» или «Прослушивание»; необработанная очередь — еженедельное (по вторникам) напоминание админу в Личном кабинете
16. Источник кейсов — база из ~1200 реальных звонков, обрабатывается пакетно (несколько звонков параллельно через шаги 2–4 раздела 6), а не по одному
17. Модуль оценки даёт сотруднику право оспорить оценку; спорные случаи разбирает админ/суперадмин вручную, итоговая оценка хранит историю пересмотра
18. «Прогресс команды» видит только руководитель (админ/суперадмин); сотрудник видит исключительно свой прогресс, без результатов коллег

## 18. Что уточнить дальше

- Точные веса баллов по каждому из 5 критериев оценки — с методологом
- Порог «зачтено/не зачтено» — нужен ли вообще
- Технический формат пакетной загрузки ~1200 существующих звонков (как именно грузятся: файлами пачкой, через API BitrixGPT, вручную по одному пачками — конкретный интерфейс загрузки не определён)
- Способ настоящей email-аутентификации на продакшене (magic link vs код vs интеграция с корпоративным SSO/Bitrix24-логином)
